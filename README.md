# vBios · Личный кабинет VPN для SHM

Клиентский интерфейс для покупки, оплаты и подключения VPN. Репозиторий: [dev-vbs/vbios-client](https://github.com/dev-vbs/vbios-client). Образ: `ghcr.io/dev-vbs/vbios-client:latest`.

> Клиент работает поверх API SHM. Он не устанавливает ядро биллинга и не настраивает серверные интеграции Telegram, платежей и тикетов автоматически.

## Что изменено

| Раздел | Возможности |
| --- | --- |
| Главная | Баланс, активные услуги, последние платежи, инструкция подключения |
| Мой VPN | Заказ тарифа, управление услугой, QR-код и ссылка подписки |
| Баланс | Пополнение доступными в SHM способами и промокоды |
| Операции | Пополнения с суммой и датой, постраничный просмотр, история списаний |
| Поддержка | Тикеты, переписка и вложения при поддержке серверного API |
| Профиль | Контакты, email, Telegram ID и настройки безопасности |
| Вход | Пароль, 2FA, Passkey и Telegram при соответствующей конфигурации |

В профиле удалены «Активные сессии», «Готовность профиля» и предварительная панель настроек дополнительного API. Telegram ID доступен для чтения; изменение выполняется через подтверждённую привязку. HWID удалён из интерфейса услуг.

Раздел уведомлений показывает текущие состояния услуг, а не полный журнал событий. В имеющемся App.tsx опрос новых ответов поддержки отключён: его подключение требует проверки серверной части. Не все новые строки интерфейса переведены на все поддерживаемые языки.

## Запуск из исходников

Требуются Git, npm и Node.js 20.19+ либо поддерживаемая более новая версия.

```bash
git clone https://github.com/dev-vbs/vbios-client.git
cd vbios-client
npm ci
cp .env.example .env
# Настройте параметры VITE_* в .env.
npm run dev
```

Для локальной разработки нужен настроенный доступ к API SHM через прокси `/shm`. `npm run dev` сам по себе не запускает биллинг.

```bash
npm run build
npm run preview
```

`npm run build` проверяет TypeScript и создаёт `dist`. Не редактируйте `dist` вручную.

### .env сборки и настройки контейнера

- `VITE_APP_NAME`, `VITE_TELEGRAM_BOT_NAME` и другие `VITE_*` используются во время сборки.
- `APP_NAME`, `SHM_URL` и другие параметры из `entry.sh` задаются через Docker Compose `environment` при запуске образа.
- `.env` рядом с Compose подставляет значения в `${...}`; он не передаёт все переменные в контейнер автоматически.
- Не добавляйте серверные токены Telegram, Remnawave, приватные VAPID-ключи и пароли в `VITE_*` или `public/config.js`.
- `SUPPORT_WIDGET_API` виден в браузере; используйте здесь только ключ, предназначенный поставщиком виджета для публичного клиента.

## Обновление GitHub через Git Bash

Откройте Git Bash **в полном клоне репозитория**, где находятся `package.json` и `.git`. Папка архива с двумя файлами не является полноценным проектом.

```bash
set -e

git rev-parse --show-toplevel
test -f package.json
git remote -v
git pull --ff-only origin main

# До следующих команд скопируйте новые файлы src из обновления в проект.
npm ci
npm run build

git add src README.md
git diff --cached --stat

if git diff --cached --quiet; then
  echo "Изменений нет. Проверьте, скопированы ли новые файлы."
else
  git commit -m "Обновлены интерфейс и документация кабинета VPN"
  git push origin main
fi
```

Не выполняйте повторный `git init`, не удаляйте `.git` и не используйте `push --force`. `Everything up-to-date` означает, что локальная ветка не содержит новых коммитов для отправки. Если main защищена, отправляйте изменения в отдельную ветку и создавайте Pull Request.

## Публикация Docker-образа

Workflow **Build and publish image** собирает проект на push в main, тегах `v*`, Pull Request и ручном запуске. Pull Request не публикует образ. Успешный push в main публикует `ghcr.io/dev-vbs/vbios-client:latest`.

Проверьте результат в [GitHub Actions](https://github.com/dev-vbs/vbios-client/actions). Для существующего GHCR-пакета репозиторий должен иметь право публикации. Для скачивания приватного пакета на сервере требуется вход в GHCR с правом `read:packages`.

Уведомления Telegram из Actions — отдельный workflow; его ошибка не объясняет результат сборки Docker. `401 Unauthorized` от Bot API означает проблему с секретом `TELEGRAM_BOT_TOKEN`.

## Обновление сервера

После успешной публикации образа:

```bash
cd /opt/shm
docker compose pull client
docker compose up -d --no-deps --force-recreate client
docker compose images client
docker compose logs --tail=50 client
```

Замените `client`, если сервис называется иначе. Push в GitHub не обновляет уже запущенный сервер автоматически. Перед обновлением сохраните конфигурацию и предыдущий тег/идентификатор образа для отката.

## Telegram: выбор способа входа

| Способ | Где используется | Что требуется |
| --- | --- | --- |
| Login Widget | Обычный браузер | Username бота без @, домен в BotFather, токен этого же бота на сервере SHM |
| Mini App | Внутри Telegram | Подписанные initData и `/telegram/webapp/auth` |
| OIDC | Браузерный переход через Telegram OAuth | Настроенный серверный OIDC, client ID и разрешённый callback |

Для Widget задайте `/setdomain` в BotFather: `bill.pbalka.ru` без протокола и пути. Имя профиля SHM, например `vBios_BOT`, не равно username бота, например `vbiosbot`.

В текущем рабочем варианте профиля привязка использует OIDC-маршрут `/telegram/web/auth/start`. Включение Widget для страницы входа само по себе не перенастраивает этот маршрут. Пример callback для вашего домена: `https://bill.pbalka.ru/shm/v1/telegram/web/callback`; он должен совпадать с серверной конфигурацией и настройками Telegram.

Подписанные данные проверяются сервером. Нельзя привязывать аккаунт простым вводом Telegram ID или доверять только `initDataUnsafe`.

## Частые проблемы

| Сообщение | Что проверить |
| --- | --- |
| `ENOENT ... package.json` | Перейдите в корень полного проекта |
| `not a git repository` | Откройте каталог клона с `.git` |
| `Everything up-to-date` | Скопируйте обновления, создайте коммит и проверьте `git status` |
| `Could not resolve ./Pages.css` | Добавьте `src/pages/Pages.css`; Linux учитывает регистр |
| Сайт остался старым | Успех Actions → pull образа → пересоздание client → проверка в приватном окне |
| `Bot domain invalid` | Домен Widget и выбранный бот в BotFather |
| `redirect_uri required` | OIDC-маршрут, фактический URL перенаправления и настройки callback |
| Не удалось войти через Telegram | HTTP-статус и Response запроса авторизации; не публикуйте cookie, initData, hash и токены |
| Тикеты/оплата не работают | Соответствующий API SHM и серверные журналы; изменения CSS не добавляют маршруты |

Сборка и проверки интерфейса на тестовых ответах API не подтверждают реальные списания, доставку тикетов и авторизацию на вашем сервере.

## Виджет поддержки [Support Bot](https://github.com/bkeenke/support-bot)

Приложение поддерживает встраивание виджета чата поддержки. Скрипт виджета загружается только после авторизации пользователя — `data-user-id` подставляется автоматически из текущей сессии.

### Переменные окружения

| Переменная | Описание | По умолчанию |
| ---------- | -------- | ------------ |
| `SUPPORT_WIDGET_URL` | URL скрипта виджета | - |
| `SUPPORT_WIDGET_API` | API-ключ виджета (передаётся в `data-api`) | - |

### Пример конфигурации

```yaml
services:
  client:
    image: ghcr.io/dev-vbs/vbios-client:latest
    environment:
      SUPPORT_WIDGET_URL: "https://widget.your-domain.com/widget.js"
      SUPPORT_WIDGET_API: "your-api-key"
```

Виджет инициализируется как:

```html
<script src="https://widget.your-domain.com/widget.js"
        data-api="your-api-key"
        data-user-id="123">
</script>
```

где `data-user-id` — это ID авторизованного пользователя в SHM.

## Push-уведомления (Тестовый)

Приложение поддерживает Web Push уведомления через Service Worker (браузерные push без PWA).

### Переменные для Push

| Переменная | Описание | По умолчанию |
| ---------- | -------- | ------------ |
| `WEB_PUSH_ENABLE` | Включить поддержку Web Push уведомлений | `false` |
| `VAPID_PUBLIC_KEY` | Публичный VAPID-ключ для Web Push | - |

### Настройка

1. Сгенерируйте VAPID-ключи (например через `npx web-push generate-vapid-keys`)
2. Укажите публичный ключ в `VAPID_PUBLIC_KEY`, приватный — в shm
3. Установите `WEB_PUSH_ENABLE=true`

в SHM нет прямой поддержки Push уведомлений, для этого нужны отдельные шаблоны, например сейчас для подписки используется POST запрос на `/shm/v1/template/subscribe` и `/shm/v1/template/unsubscribe` для отписки

После авторизации в шапке приложения появится кнопка 🔔 — пользователь сам управляет подпиской.

### Открытие уведомления из URL

При клике на push-уведомление браузер открывает приложение. Если в URL присутствуют параметры `_nt` (заголовок) и `_nb` (текст), приложение автоматически показывает всплывающее уведомление внутри интерфейса:

```text
https://your-domain.com/?_nt=Заголовок&_nb=Текст+уведомления
```

### iOS

На iOS Web Push работает только в **Safari 16.4+** при условии, что приложение добавлено на главный экран (режим PWA / Home Screen). В обычном браузере на iOS push-уведомления недоступны.

## Добавление кастомного языка

Можно подключить любой язык, не входящий в список встроенных, без пересборки образа.

### 1. Создать файл перевода

Скопируйте один из встроенных файлов (`public/locales/en.json`) как шаблон и переведите все значения.
Обязательно укажите блок `config` в корне файла:

```json
{
  "config": {
    "code": "cn",
    "label": "简体中文",
    "flag": "🇨🇳"
  },
  "common": {
    ...
  }
}
```

| Поле | Описание |
| ---- | -------- |
| `code` | Код языка (должен совпадать с именем файла, например `cn` → `cn.json`) |
| `label` | Название языка в переключателе |
| `flag` | Флаг-эмодзи |

### 2. Подключить файл через volume

```yaml
services:
  client:
    image: ghcr.io/dev-vbs/vbios-client:latest
    environment:
      CUSTOM_LANGS: "cn"
    volumes:
      - "./cn.json:/app/locales/cn.json"
```

Несколько языков указываются через запятую:

```yaml
CUSTOM_LANGS: "cn,kk"
```

### 3. Валидация

При загрузке приложение проверяет каждый кастомный язык:

- наличие `config.label` и `config.flag` — файл появится в переключателе
- количество переведённых ключей — если переведено **менее 50%** ключей относительно `en.json`, язык игнорируется с предупреждением в консоли

## Категории услуг для VPN/Proxy

Для отображения **QR-кода** и **ссылки подписки** в деталях услуги, категория услуги должна соответствовать одному из следующих паттернов:

### VPN (WireGuard конфигурация)

Категория должна **начинаться** с одного из значений:

- `vpn`
- `wg`
- `awg`

Примеры валидных категорий: `vpn`, `vpn-wg`, `vpn-awg-nl`, `awg-premium`, `wg-fast`

**Storage ключ:** `vpn{user_service_id}` (например: `vpn123`)

### Proxy (Marzban/Remnawave подписка)

Категория должна содержать одно из слов:

- `remna`
- `remnawave`
- `marzban`
- `marz`
- `mz`

Примеры валидных категорий: `marzban`, `remnawave`, `mz-premium`, `proxy-marz`

**Storage ключи:**

- `vpn_mrzb_{user_service_id}` (например: `vpn_mrzb_123`)
- `vpn_remna_{user_service_id}` (например: `vpn_remna_123`)

### Прочие категории

Следующие категории отображаются как есть (без QR/ссылки):

- `web_tariff` — Тарифы хостинга
- `web` — Web хостинг
- `mysql` — Базы данных
- `mail` — Почта
- `hosting` — Хостинг

Все остальные категории группируются как "Прочее".
